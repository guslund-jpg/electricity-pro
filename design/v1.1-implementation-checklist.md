# v1.1 Implementation Checklist

> Delivery checklist for forecast prices and scheduling insights based on the [v1.1 design proposal](./v1.1-forecast-prices-and-scheduling-insights.md).

---

## 1. Forecast data foundation

- [x] Identify the exact Nord Pool future-price source available through Home Assistant.
- [x] Confirm that the native Nord Pool integration uses split entities plus the `nordpool.get_prices_for_date` action instead of exposing raw interval lists on the main current-price sensor.
- [x] Confirm that the action returns interval `start`, `end` and `price` fields, with timestamps in UTC and prices in requested currency per MWh.
- [x] Define the internal normalized forecast interval structure (`ForecastInterval` dataclass in `forecast.py`).
- [x] Decide where forecast ingestion should live relative to the existing provider and coordinator modules (separate `nordpool.py` ingestion layer, coordinator-owned cache).
- [x] Decide whether restart persistence is required or whether source rehydration is sufficient (source rehydration on startup is sufficient; implemented in `coordinator.async_start`).

---

## 2. Forecast normalization

- [x] Parse action-returned future intervals into timezone-aware start and end datetimes.
- [x] Derive interval resolution from interval boundaries instead of assuming hourly data (`resolution_minutes` property).
- [x] Normalize raw market price, currency, area and publication timestamp.
- [x] Convert source prices from currency per MWh to currency per kWh before calculations.
- [x] Reject or ignore malformed intervals according to documented behavior (raises `ValueError` on malformed input).
- [x] Discard expired intervals before scheduling calculations run (`interval.start >= now` filter) and recalculate cached insights every 15 minutes.
- [x] Detect gaps and overlaps explicitly (gap and overlap checks in `find_cheapest_continuous_window` and `find_price_direction`).

---

## 3. Effective future price calculation

- [x] Reuse the existing pricing adjustment philosophy for effective future prices.
- [x] Produce both raw market price and effective price in the normalized interval model.
- [x] Verify behavior when variable fee and markup options are absent (defaults to zero adjustment).
- [x] Verify behavior when configured adjustments are present (tested in `test_forecast_insights.py`).

---

## 4. Insight calculations

- [x] Implement cheapest upcoming single-interval calculation (cheapest 1h window covers single-interval hourly and multi-interval quarter-hour cases).
- [x] Implement cheapest continuous multi-interval window selection for the initial supported durations (1h, 2h, 3h in `find_cheapest_continuous_window`).
- [x] Implement next inexpensive window detection relative to a configured threshold (`find_next_inexpensive_1h_window`).
- [x] Implement simple near-term price direction classification (`find_price_direction`; returns rising / falling / stable).
- [x] Ensure calculations depend only on normalized intervals.
- [x] Return unavailable results when required future data is missing or incomplete (all functions return `None`).

---

## 5. Home Assistant integration

- [x] Decide which forecast outputs become sensors and which details live in attributes (start-time timestamp sensors with window metadata in attributes; companion average effective price sensors).
- [x] Add forecast and scheduling insight entities (cheapest 1h/2h/3h window start and average effective price; price direction; next inexpensive 1h window start).
- [x] Ensure entity names, unique IDs and device metadata follow project conventions.
- [x] Recompute insights when forecast intervals change (`_recalculate_forecast_insights` called after interval refresh).
- [x] Recompute insights when pricing adjustment options change (recalculation uses `provider_data.grid_fee_per_kwh` and `provider_data.tax_per_kwh` at recalculation time).
- [x] Ensure stale insights expire correctly as time advances (15-minute coordinator lifecycle tick plus `interval.start >= now` filtering).

---

## 6. Time and lifecycle behavior

- [x] Validate local timezone handling across all interval calculations (all datetimes are timezone-aware; `ForecastInterval.__post_init__` enforces this).
- [x] Cover daylight-saving transitions with focused tests (DST spring-forward and fall-back tests in `test_forecast_insights.py`).
- [x] Confirm behavior when tomorrow publication and `nordpool.get_prices_for_date` disagree or change at different times (the coordinator retries the native action after 13:00 and degrades forecast entities gracefully on failure).
- [x] Confirm behavior when Nord Pool tomorrow data is delayed or partially published (retrieval is retried every 15 minutes until a valid response is cached).
- [x] Confirm restart behavior and data refresh flow (coordinator calls `_async_refresh_forecast_intervals` in `async_start`).
- [x] Use a conservative 15-minute lifecycle tick only for configured forecasts; fetch today once per delivery date and tomorrow only after 13:00 until successfully cached.
