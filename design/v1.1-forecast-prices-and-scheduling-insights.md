# Design Proposal

> v1.1 introduces future-price forecasting and scheduling insights for Nord Pool users while keeping the internal design clean enough to support broader forecast sources later.

---

## Summary

Electricity Pro v1.1 will add future-price awareness to the integration so that homeowners and automations can reason about upcoming electricity cost windows instead of only current and historical values.

The first implementation will require Nord Pool as the source of future prices. This keeps the release scope practical and aligned with the most relevant initial market while avoiding a premature multi-provider forecast framework.

Internally, however, Nord Pool forecast data will be converted into a small normalized Electricity Pro interval model before any insight logic runs. This keeps provider-specific parsing isolated and allows future extensions without redesigning the calculation layer.

---

## Problem

Electricity Pro currently helps users understand current conditions and recent electricity usage, but it does not yet answer a key planning question: when will electricity be cheaper later today or tomorrow?

For households with flexible consumption such as EV charging, dishwashers, laundry, water heating or other shiftable loads, the useful decision is often not about the current price but about the best upcoming window.

Without future-price handling, users must inspect separate Nord Pool cards or dashboards and manually interpret the best time to run appliances.

---

## Homeowner Question

> What is the cheapest upcoming time to use electricity, and should I wait?

---

## Goals

- Add normalized future-price interval support for upcoming Nord Pool prices.
- Handle hourly and quarter-hour interval resolution through one internal model.
- Produce practical scheduling insights that are easy to use in dashboards and automations.
- Keep Nord Pool-specific assumptions isolated to the forecast ingestion layer.
- Define explicit behavior for missing, delayed, overlapping or incomplete future intervals.
- Preserve correct local-time and daylight-saving behavior.

---

## Non-Goals

- Full provider-independent forecast-source selection in v1.1.
- Direct appliance control or optimization loops.
- Recommendation engines that estimate appliance-specific consumption profiles.
- Generic support for every possible electricity market format.
- Reworking the current provider layer that reads existing Home Assistant entities for live data.

---

## Proposed Design

### Product stance

Forecast prices and scheduling insights in v1.1 require the native Home Assistant Nord Pool integration.

Electricity Pro will therefore remain provider-independent for its existing live-measurement inputs, but forecast-based insights will initially depend on Nord Pool being available in Home Assistant.

This is a deliberate scope choice rather than a long-term architectural limitation.

### Internal forecast model

Nord Pool future prices should be converted as early as possible into a small internal interval model before any scheduling logic runs.

The model should contain at least:

- interval start
- interval end
- market price
- effective price
- currency
- price area
- resolution
- publication timestamp

Design constraints:

- timestamps must be timezone-aware;
- intervals must represent half-open ranges `[start, end)`;
- resolution must be derived from interval boundaries rather than assumed globally;
- effective price must be derived from the same fee and markup configuration philosophy already used for current effective price;
- source prices returned in currency per MWh must be normalized to currency per kWh before entering the internal interval model.

This is not a public multi-provider contract yet. It is an internal normalization boundary that keeps the insight logic independent of Nord Pool payload details.

### Forecast ingestion

A Nord Pool-specific forecast ingestion component should:

- call the native Home Assistant Nord Pool action `nordpool.get_prices_for_date` for the required date, area and currency;
- read returned intervals and relevant metadata from the action response;
- validate interval ordering and completeness;
- normalize timestamps and prices into the internal forecast model;
- convert returned market prices from currency per MWh to currency per kWh;
- reject or ignore malformed intervals according to documented rules.

The current native Nord Pool sensor entities are useful for metadata and manual validation, but they should not be treated as the primary source of raw forecast intervals. Nord Pool-specific behavior such as expected publication timing, available horizon length and source quirks should remain in this layer only.

### Time handling

Future-price logic must treat time handling as a first-class design concern.

Rules:

- store and compare timezone-aware datetimes only;
- preserve local-wall-clock meaning for user-facing sensors and attributes;
- avoid assuming a day always contains 24 one-hour slots;
- support daylight-saving transitions that create shorter or longer local days;
- allow mixed forecast availability where only part of the next day has been published.

Scheduling calculations should operate on actual interval boundaries rather than on an assumed list of hourly indexes.

### Missing or imperfect forecast data

The design must explicitly handle:

- no future intervals available yet;
- delayed Nord Pool publication;
- action responses for tomorrow before publication;
- gaps between intervals;
- overlapping intervals;
- incomplete next-day publication;
- intervals that have already expired.

Recommended behavior:

- expired intervals are discarded;
- overlapping intervals are treated as invalid input and excluded from scheduling calculations unless a clear source-of-truth rule exists;
- gaps prevent any continuous-window insight from spanning across the missing time;
- `binary_sensor.nord_pool_<area>_tomorrow_price_available` should be treated as a useful native readiness signal, but the forecast adapter must still validate the action response content itself;
- insights expose unavailable state when insufficient future data exists for the requested calculation.

This approach favors transparent behavior over hidden guesswork.

### Effective future prices

Scheduling insights should use effective future prices, not only raw market prices, when the user has configured variable fees or tax and markup adjustments.

That means the forecast pipeline should produce:

- raw future market price normalized to currency per kWh for transparency;
- effective future price in currency per kWh for practical automation and decision-making.

This keeps future insights consistent with the current effective-price concept already exposed by Electricity Pro.

### Insight calculations

v1.1 should focus on informational insights suitable for dashboards and automations.

Initial candidates:

- cheapest upcoming single interval;
- cheapest continuous two-interval window;
- cheapest continuous multi-hour or multi-interval window for fixed supported durations;
- next inexpensive window relative to a configured threshold;
- near-term price direction, such as rising, falling or mixed.

Design rule:

Nord Pool-specific assumptions may exist in forecast ingestion, but insight calculations must only consume normalized intervals.

### Home Assistant entity shape

Forecast insights should be exposed as standard Home Assistant entities with attributes that explain the result.

Likely outputs include:

- sensor for cheapest upcoming start time;
- sensor for cheapest upcoming window average price;
- sensor for next inexpensive window start;
- sensor for price direction;
- attributes containing window start, window end, duration, compared interval count, currency and area.

Entity definitions should prefer simple sensor states with explanatory attributes rather than complex nested structures.

### Refresh and persistence

The forecast design should define predictable lifecycle behavior across updates and restarts.

Requirements:

- refresh when new Nord Pool action-retrievable dates become available or when the relevant Home Assistant Nord Pool entities indicate an update;
- persist enough information to survive Home Assistant restarts cleanly if needed by the implementation approach;
- recompute insights whenever future intervals or pricing adjustments change;
- expire stale intervals automatically as time advances.

The implementation should avoid introducing unnecessary polling if Home Assistant already exposes suitable update signals from the Nord Pool integration, such as the tomorrow-availability binary sensor and last-updated metadata.

---

## User Impact

Homeowners gain a clearer answer to the next-step question in daily electricity usage.

Instead of manually reading tomorrow's prices, they can use Electricity Pro sensors to:

- decide whether to run flexible appliances now or later;
- build automations that wait for cheaper windows;
- understand whether prices are expected to rise or fall soon;
- compare raw market prices with their effective all-in price.

This adds planning value without taking direct control away from the homeowner.

---

## Technical Impact

Affected components are expected to include:

- a new forecast normalization module or helper;
- Nord Pool-specific forecast ingestion logic built around the native `nordpool.get_prices_for_date` action;
- source-unit normalization from currency per MWh to currency per kWh;
- insight calculations for continuous future windows;
- sensor entities for forecast and scheduling outputs;
- configuration support for any required forecast-related options.

Likely architectural implications:

- existing live-data provider code remains focused on current source entities;
- forecast ingestion may sit beside, not inside, the current provider layer if its lifecycle differs materially from live-state normalization;
- calculation code should remain deterministic and independently testable.

No new external Python dependency should be introduced unless clearly required.

---

## Testing

Testing should cover both deterministic calculation behavior and Home Assistant integration behavior.

- Unit tests for interval normalization, gap detection, overlap rejection and window selection.
- Unit tests for effective future-price calculation with configured adjustments.
- Unit tests for daylight-saving and timezone edge cases.
- Integration tests that simulate Nord Pool forecast updates through Home Assistant.
- Entity tests for unavailable states when future data is incomplete or missing.
- Manual verification against real Nord Pool publication timing and example dashboards.

---

## Alternatives Considered

### Full provider-independent forecast framework in v1.1

Rejected for now because it adds design and testing cost before there is a confirmed second forecast source.

The extra abstraction would provide limited immediate user value and slow delivery of practical insights.

### Pure Nord Pool-specific implementation with no internal normalization boundary

Rejected because it would make future insight logic tightly coupled to one source format and likely increase rewrite cost in later releases.

### Direct device-control scheduling in v1.1

Rejected because automatic control needs a clearer safety and recommendation model than this release is intended to provide.

---

## Future Extensions

This design should allow future releases to add:

- additional future-price sources beyond Nord Pool;
- appliance-specific recommendation logic;
- estimated savings calculations for delayed execution;
- start-time recommendation sensors for EV charging or household appliances;
- more flexible duration-based scheduling calculations;
- optimization features built on top of the same normalized interval model.

If and when multiple forecast sources become real requirements, the normalized internal interval model can be promoted into a formal provider contract.
